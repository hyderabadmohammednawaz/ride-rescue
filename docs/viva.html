01 The thirty-second answer

Say this

RideRescue connects a stranded two-wheeler rider with the nearest available mechanic in seconds, tracks that mechanic live on a map, and runs a spare-parts marketplace alongside it. Four roles — customer, mechanic, vendor, admin. Node and Express with Socket.IO for real time, MongoDB for geospatial search, Next.js for web, React Native for the phone. Four explainable AI features. It is deployed and running on real accounts with real SMS verification and a real payment gateway in test mode.

That last sentence is the one that separates this from a prototype. Lead with it.

02 Architecture, and why each choice

Why MongoDB and not MySQL

The central query is “available mechanics within N km, nearest first”. MongoDB answers that natively with a 2dsphere index and $near. MySQL would need spatial extensions or bounding-box arithmetic in application code. Bookings also carry naturally nested, variable-shape data — statusHistory[], partsUsed[] — which suits documents better than join tables.

Why Socket.IO and not polling

Live tracking and chat need push. Polling every three seconds across many customers wastes requests and still feels laggy; a socket delivers the moment the mechanic's phone reports a new position.

Why one process serves both REST and sockets

They share JWT verification and the same Mongoose models. Splitting them would duplicate auth and add a message bus for no benefit at this scale.

Why two frontends rather than one codebase

The web app is four information-dense dashboards where routing and server rendering matter. The phone app is two focused flows needing GPS and background location. Sharing UI code would compromise both.

03 The four AI features

Expect the heaviest probing here. Give the honest framing before you are asked:

Say this first

These are explainable multi-criteria decision models, not neural networks, and that is deliberate. Every output can be justified in a sentence, they work from day one with no training data, and they run inside a single request. A learned model is the next iteration, once there are enough completed bookings to train on.

That answer is stronger than pretending, because the follow-up is always “where is your training data?”

3.1 — Mechanic matching

Weighted scoring across five signals, re-weighted for emergencies:

SignalEmergencyNormal
Distance0.500.32
Rating0.200.30
Availability0.120.10
Experience0.100.18
Workload0.080.10

Why the weights shift: in a breakdown, who arrives soonest dominates — a superb mechanic forty minutes away is the wrong answer. For a planned service, quality matters more than speed.

Unrated mechanics score 3.5/5 rather than zero, so a new joiner is not permanently buried by a cold-start penalty. Every result carries readable reasons: “Only 0.4 km away · 5 years experience · Free right now”.

Live evidence: booking RR-GXARBY recorded “Auto-assigned by AI match (score 0.7674)” and assigned in under one second.

3.2 — Parts recommendation

Content-based filtering: matches parts to the customer's specific bike make and model, weighted by what past bookings for similar vehicles consumed. Deliberately not collaborative filtering — that needs a user base the project does not yet have.

3.3 — Predictive maintenance

Dual-axis prediction over eight components: whichever of kilometres ridden or months elapsed comes first triggers the due date — mirroring how manufacturers actually specify service intervals. Outputs a health score and a per-component urgency list.

3.4 — Chatbot

Keyword-overlap intent classification across nine intents, each with a handler that queries live data — so “where is my mechanic” returns the real current ETA, not a canned string.

04 Geospatial search

  • Coordinates are stored GeoJSON [longitude, latitude] — that order, which is the usual stumbling block since everyone says “lat, long” aloud.
  • A 2dsphere index makes $near an index scan rather than a collection scan, and treats the Earth as a sphere rather than a flat plane.
  • The dispatch filter: role: mechanic, isBlocked: false, isAvailable: true, within 20 km.
Volunteer this

Distance and ETA are straight-line, computed with the haversine formula. Real road routing would need OSRM or a routing API — that is the next step.

Saying it first turns a weakness into evidence that you understand the system's edges. “Why 20 km?” — beyond that a two-wheeler mechanic is not a practical rescue; it is a named constant, not a magic number scattered through the code.

05 Real-time tracking

  1. The mechanic's phone emits location:update every four seconds or every 20 metres of movement, whichever comes first.
  2. The server recomputes distance and ETA to the pickup point, saves them, and broadcasts booking:location to that booking's private room.
  3. Both parties join that room only after the server verifies they belong to the booking — the room name alone is not authorisation.

JWT is verified on the socket handshake too, not just on REST calls. Blocked accounts are rejected at both entry points.

A demo simulator moves seeded mechanics so tracking animates without a second phone. It deliberately skips accounts with a Firebase uid — real users. Both would otherwise write every few seconds and fight each other, and the simulator would corrupt the real mechanic's stored position.

Your strongest security answer

The Razorpay signature is verified against the order id stored on our own payment record, never the one the browser sends back. A signature only proves that some order was paid. If we trusted a client-supplied order id, a valid signature from a different, cheaper order could be replayed against an expensive one.

Say these yourself

The JWT lives in localStorage, which JavaScript can read — an httpOnly cookie is stricter but complicates the mobile client. There is no rate limiting on login; express-rate-limit is the first thing to add. Naming your own limitations reads as engineering maturity; being caught out by them does not.

07 Auth and the DLT story

“How do you send OTPs? Isn't SMS in India regulated?”

Say this

Yes — commercial SMS to Indian numbers requires TRAI DLT registration: entity, header and template approval, which needs a registered business. A student project cannot get that. We use Firebase Phone Authentication, where Google is the DLT-registered sender, so the requirement does not fall on us.

How the trust actually works — this is the part that matters. The phone talks to Firebase directly. Firebase sends the SMS and checks the code, then returns a signed ID token. Our backend verifies that signature with the service-account key. That verification is what proves the caller controls the number; otherwise a client could simply post any phone number it liked.

Web and mobile use the same endpoints, so one identity works on both. Web additionally needs a reCAPTCHA verifier — a browser has no app-signature equivalent to prove it is not a bot — and that verifier is single-use, which is why each send builds a fresh one.

08 Payments

  1. Create. The server creates a Razorpay order and stores its id. Checkout cannot open without one, and it binds the payment to an amount we chose.
  2. Pay. The browser opens Razorpay's own sheet. Card details are entered in their iframe and never touch our page or server — which is why checkout.js loads from their CDN rather than being bundled.
  3. Confirm. The server recomputes HMAC-SHA256(order_id | payment_id) and compares it in constant time against the returned signature.

Wallet and cash never reach the gateway — the wallet is our own ledger, cash settles in person.

Proven live: payment PAY-A9Y3KQT7 reached success with real ids order_TR6BDZCENcEF4K and pay_TR6BNfBuLT5dwk. A forged signature was rejected with HTTP 400.

A detail worth volunteering

A declined payment stays pending, not failed. No signature comes back, so nothing is confirmed and the customer can retry. Only a tampered signature marks it failed. Those are genuinely different situations and the code distinguishes them.

If asked why test mode: live mode needs KYC and per-method bank onboarding — roughly ten working days. Nothing in the code differs between test and live; only the keys.

09 Deployment choices

“Why Render for the backend when the web app is on Vercel?” — a very likely question.

Say this

Vercel and Netlify are serverless. A serverless function cannot hold a persistent WebSocket, so live tracking and chat — the two headline features — would not work. Render runs a real long-lived Node process. The Next.js frontend has no such constraint, so it sits on Vercel where it belongs.

Why Atlas and not the embedded database in production? Hosted platforms wipe local disk on every restart and redeploy; every booking and account would vanish. The embedded MongoDB exists so the project runs on a laptop with nothing installed.

Trade-off to acknowledge: the free tier sleeps after 15 minutes and takes ~50 seconds to wake. Fly.io's free allowance does not force a sleep.

10 War stories

Examiners rate debugging insight highly, and these are all true. Each one shows a different class of failure.

Silent data loss on seeding

The embedded MongoDB was killed before it checkpointed, so the last writes vanished — the seed reported success while data was missing. Fixed with an fsync before shutdown.

“The process exited cleanly” is not the same as “the data is on disk”.

A deployment that looked fine and was broken

The live site called localhost:5000. Those values are inlined into the client bundle at build time, and the variable had been marked Sensitive — a flag that withholds it from anything the browser can read, which is exactly what inlining is.

A security flag applied to the wrong kind of value fails silently.

Accounts created but unusable

Web signup created the account, then sent users to an OTP screen no code could reach, because DEV_MODE is off in production. Login then returned 403 for unverified accounts.

The failure sat at a seam between two components that were each individually correct.

A config that produced a dead end

Restricting the payment sheet to UPI produced “No appropriate payment method found” — UPI was disabled on the account, so the sheet resolved to nothing.

Prefer degrading to a default over enforcing a preference that can be empty.

A race disguised as an override

A comment claimed a real device would “simply override” the simulator. Both wrote every few seconds — that is a race, not an override, and it corrupted the real mechanic's stored position.

Comments describe intent; only the code describes behaviour.

11 Rapid-fire

What if no mechanic accepts?
Auto-assigned to the highest scorer; a decline reassigns to the next best; if nobody is in range the booking stays pending, surfaces in the admin's unassigned filter, and an admin can assign manually using the same ranking.
How do you stop a mechanic billing for work never done?
Two gates — the customer's 4-digit start OTP, and the QR token on the completed record.
How is a customer stopped from reading someone else's booking?
Role guard and ownership check. The role alone is not enough — that distinction is the point.
What is your test coverage?
A 59-check end-to-end regression covering auth, access control, the booking lifecycle, all four AI features, the store and both dashboards. Be honest about two things — these are integration checks rather than unit tests, and the full 59 pass against a seeded database. Run against production, the checks that sign in as the seeded customer and mechanic fail by design: those accounts were deleted so that side of the app runs on real phone-verified signups. Knowing why your own suite fails in one environment is a better answer than claiming it always passes.
How many users can it handle?
Free tier: 512 MB RAM, shared CPU — fine for a demo, not real traffic. It scales by moving Socket.IO to a Redis adapter and running multiple instances behind a load balancer; Atlas scales separately.
What would you improve with more time?
Rate limiting on auth, httpOnly refresh tokens, real road routing via OSRM, a learned ranking model trained on completed bookings, and unit tests alongside the integration suite.

12 Before you walk in

  • Health URL opened a minute early, so the API is awake
  • Web app loaded and logged in on one screen
  • Both phones charged, same network, location permission granted
  • Demo path one rehearsed: SOS → auto-assign → live track → OTP start → complete → pay
  • Demo path two rehearsed: store → cart → checkout → invoice
  • Payment set to Netbanking — the mock bank page has Success and Failure buttons, so there is nothing to type
  • Architecture diagram open in the README
  • An honest answer ready for “what would you do differently?”
Never during the demo

Do not run npm run seed against the live database. It deletes every collection including users — the real accounts, the completed bookings and the payment records would all go, with no undo.
